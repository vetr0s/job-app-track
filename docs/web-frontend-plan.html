Web frontend plan

2026-08-29job-app-track @ 989e8e9Design and handoff

The web frontend is a second frontend over the same Store the CLI uses. This session landed a running skeleton: a stdlib http.server bound to a route table, Jinja2 templates packaged with the wheel, a jat serve command, htmx 4.0.0 vendored, and the pipeline board as the one worked example. Every other route is registered and returns 501 until its handler is written. The next agent fills in the handlers and templates for full CLI parity, using htmx 4.0 for the interactive parts. Nothing in core/ needs to change; the Store contract already carries this.

What runs today

Verified jat serve boots, opens the database once, and serves. GET / renders the pipeline board from live data. GET / with an HX-Request header returns just the board fragment. Static assets serve with correct content types. Unknown paths are 404, wrong method is 405, path traversal on /static/ is refused. The wheel contains the templates and the vendored htmx file. 74 tests pass. 
jat serve                       # http://127.0.0.1:8765
jat serve --host 0.0.0.0 --port 9000
jat --db /tmp/demo.db serve     # same --db / $JAT_DB resolution as every command

Architecture

Seam
Route handlers call Store methods and pass the frozen dataclasses straight to a template. The web layer adds no domain logic. This is the same seam the CLI crosses.
Concurrency
Single-threaded HTTPServer. One SQLite connection, requests served one at a time. Correct for one user on a private network, and it means no connection pool and no thread-safety questions. If a later need forces concurrency, the change is a Store per request, not a shared connection across threads.
Templating
Jinja2, the one runtime dependency added for this layer. Autoescape is on. PackageLoader reads from web/templates/, which the wheel packages via pyproject.toml artifacts.
Verbs
GET and POST only. Forms post; there is no PUT or DELETE. htmx 4 can issue any method over fetch(), but forms plus POST cover every CLI mutation and keep the handler side simple. Adding a verb later is one do_VERB method in web/server.py.

The handler contract

A handler takes a Request and returns a Response. dispatch() matches method plus path against ROUTES, builds the Request, and calls the handler.

@dataclass(frozen=True, slots=True)
class Request:
    method: str
    path: str
    params: dict[str, str]   # captured from the pattern, e.g. {"id": "4"}
    query: dict[str, str]    # first value per key
    form: dict[str, str]     # parsed x-www-form-urlencoded body
    headers: Mapping[str, str]
    store: Store
    @property
    def is_htmx(self) -> bool   # HX-Request header is "true"

@dataclass(frozen=True, slots=True)
class Response:
    body: str = ""
    status: int = 200
    headers: dict[str, str] = {}
    @classmethod
    def html(body, status=200) -> Response
    @classmethod
    def redirect(location) -> Response    # 303
    @classmethod
    def text(body, status) -> Response

@dataclass(frozen=True, slots=True)
class Route:
    method: str
    pattern: str    # "/applications/<int:id>", also <str:name>
    handler: Callable[[Request], Response]

Pattern captures are <int:name> and <str:name>. An int capture that does not match \d+ falls through to 404, so a bad id never reaches a handler.

Read handlers

Branch on req.is_htmx. A normal navigation returns page(...), a full document. An htmx request returns fragment(...), the same inner markup with no chrome, so the client can swap it in place. pipeline() in web/routes.py is the pattern to copy: it renders pipeline.html for a navigation and _board.html for a swap, and pipeline.html just {% include "_board.html" %}.

Write handlers

Read req.form, call the Store method, then return the swapped fragment for an htmx caller or Response.redirect(...) for a plain form post. Use the enum tuples in core/enums.py to build <select> options and to keep the template honest about valid values.

This is the same split as cli._USER_ERRORS. Expected failures are concise, unexpected ones stay loud. For an htmx request the 4xx body should be a small fragment so the message lands in the page; handlers own that framing.

htmx 4.0

4.0.0 shipped on 2026-08-28, one day before this plan. It is a real major version with breaking changes, not a point release. The relevant points:

Pin the version
2.x stays the npm latest tag until early 2027, so an unversioned CDN URL serves 2.x. The file is vendored at web/static/htmx-4.0.0.min.js and referenced with the version in the name. Keep it that way.
Explicit inheritance
Attributes like hx-target and hx-swap no longer inherit to descendants by default. Put the attribute on the element that makes the request, or add the :inherited suffix on the parent where sharing is intended.
Event names
Standardised to htmx:phase:action, for example htmx:after:swap. Matters only if you wire JS listeners.
Morph swaps
Built in via idiomorph. hx-swap="morph" on the board re-renders after a status change without losing scroll position or focus. Good fit for the pipeline and any list that swaps often.
<hx-partial>
The 4.0 replacement for hand-rolled out-of-band swaps. Use it to update the nav counts alongside the main swap after a write.
History
Back-navigation re-fetches the page instead of restoring from localStorage. No action needed here; every page is a cheap Store read.

Docs for 4.0 are at four.htmx.org, not htmx.org. The team ships an upgrade-checker CLI and LLM skill files for migrating 2.x markup, which is worth a look if you copy snippets from older tutorials.

Conventions to hold

  • Handlers stay thin. Any logic that is not "read the form, call the Store, pick a template" belongs in core/.
  • Fragment templates are named with a leading underscore.
  • Every enum-valued <select> is built from core/enums.py, never a literal list in a template.
  • No new runtime dependency without asking. Jinja2 is the whole budget.
  • The web layer never imports from cli.py and the CLI never imports from web/ except the one lazy import inside the serve branch.

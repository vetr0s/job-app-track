Job application tracker: implementation plan

2026-08-29job-app-track @ cfeb27dHistorical plan

Build a stdlib-only Python package with a normalized SQLite schema, a versioned SQL migration runner, and a thin domain layer that a CLI drives now and a local web app drives later. The domain layer is a Store facade returning frozen dataclasses; both frontends parse input, call Store methods, and format the result, and neither touches SQL. The schema is the one expensive decision here. It is now approved, so the scaffold and 0001_init.sql land as the first commit and everything after is filling in function bodies against a fixed contract.

Historical document This plan records the initial design. The implementation is complete. Several contracts changed during verification. Applications now select postings by role ID. Store transactions compose through savepoints. Migration files cannot control transactions. Use README.md, jat --help, and the current tests for executable instructions.

Constraints and decisions

Language
Python 3.13, managed with uv. Build backend hatchling (the uv init default).
Dependencies
Standard library only at runtime: sqlite3, argparse, pathlib, importlib.resources, json, dataclasses. No third-party packages.
Interface now
A CLI, installed as the jat console script and runnable as python -m job_app_track.
Interface later
A single-user local web app, reachable from a phone over a private VPN. Out of scope for this plan. The domain seam is designed so the web app is a second frontend over the same Store, not a rewrite.
Schema scope
Normalized: companies, roles, applications, contacts, interviews, plus an append-only status timeline and a contact-to-application join.
Schema changes
Numbered .sql files under migrations/, applied on startup, tracked by PRAGMA user_version.
Database location
$JAT_DB if set, else ~/.local/share/job-app-track/jat.db, overridable per invocation with --db. Created on jat init.
Enums
Stored as TEXT with CHECK constraints. The canonical lists also live in core/enums.py for input validation and, later, web form options. The migration copy is frozen at its version; the Python copy is current. This duplication is expected.

Data model

Seven tables. A role is a specific posting at a company. An application is one pursuit of one role, and carries a denormalized status column for fast list and board queries. The authoritative history is application_status_events, which is append-only; Store writes an event and updates applications.status in the same transaction. Timestamps are ISO-8601 UTC text (datetime('now')), which sorts lexically and reads plainly in the sqlite3 shell.

Note Foreign keys are off by default in SQLite. The connection helper issues PRAGMA foreign_keys = ON on every connect, so the ON DELETE rules below actually fire. 
-- migrations/0001_init.sql

CREATE TABLE companies (
  id          INTEGER PRIMARY KEY,
  name        TEXT NOT NULL UNIQUE,
  website     TEXT,
  notes       TEXT,
  created_at  TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE roles (
  id           INTEGER PRIMARY KEY,
  company_id   INTEGER NOT NULL REFERENCES companies(id) ON DELETE CASCADE,
  title        TEXT NOT NULL,
  location     TEXT,
  arrangement  TEXT CHECK (arrangement IN ('onsite','hybrid','remote')),
  comp_min     INTEGER,
  comp_max     INTEGER,
  url          TEXT,
  jd_text      TEXT,
  notes        TEXT,
  created_at   TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE applications (
  id             INTEGER PRIMARY KEY,
  role_id        INTEGER NOT NULL REFERENCES roles(id) ON DELETE CASCADE,
  status         TEXT NOT NULL DEFAULT 'wishlist' CHECK (status IN (
                   'wishlist','applied','screen','interview',
                   'offer','rejected','accepted')),
  source         TEXT CHECK (source IN (
                   'board','referral','recruiter','cold','event','other')),
  resume_version TEXT,
  interest       TEXT CHECK (interest IN ('low','medium','high')),
  applied_at     TEXT,
  notes          TEXT,
  created_at     TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at     TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE application_status_events (
  id             INTEGER PRIMARY KEY,
  application_id INTEGER NOT NULL REFERENCES applications(id) ON DELETE CASCADE,
  status         TEXT NOT NULL,
  occurred_at    TEXT NOT NULL DEFAULT (datetime('now')),
  note           TEXT
);

CREATE TABLE contacts (
  id          INTEGER PRIMARY KEY,
  company_id  INTEGER REFERENCES companies(id) ON DELETE SET NULL,
  name        TEXT NOT NULL,
  title       TEXT,
  email       TEXT,
  phone       TEXT,
  linkedin    TEXT,
  notes       TEXT,
  created_at  TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE application_contacts (
  application_id INTEGER NOT NULL REFERENCES applications(id) ON DELETE CASCADE,
  contact_id     INTEGER NOT NULL REFERENCES contacts(id) ON DELETE CASCADE,
  relationship   TEXT NOT NULL CHECK (relationship IN (
                   'recruiter','referrer','interviewer','hiring_manager','other')),
  PRIMARY KEY (application_id, contact_id, relationship)
);

CREATE TABLE interviews (
  id             INTEGER PRIMARY KEY,
  application_id INTEGER NOT NULL REFERENCES applications(id) ON DELETE CASCADE,
  kind           TEXT CHECK (kind IN (
                   'phone_screen','technical','system_design',
                   'behavioral','onsite','hiring_manager','hr','other')),
  scheduled_at   TEXT,
  duration_min   INTEGER,
  location       TEXT,
  contact_id     INTEGER REFERENCES contacts(id) ON DELETE SET NULL,
  outcome        TEXT NOT NULL DEFAULT 'pending' CHECK (outcome IN (
                   'pending','passed','failed','cancelled','no_decision')),
  prep_notes     TEXT,
  debrief_notes  TEXT,
  created_at     TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE INDEX idx_roles_company        ON roles(company_id);
CREATE INDEX idx_applications_role     ON applications(role_id);
CREATE INDEX idx_applications_status   ON applications(status);
CREATE INDEX idx_status_events_app     ON application_status_events(application_id);
CREATE INDEX idx_app_contacts_contact  ON application_contacts(contact_id);
CREATE INDEX idx_interviews_app        ON interviews(application_id);

Domain types

One frozen dataclass per table, used as read models only. Write methods take keyword arguments and return the created or updated dataclass. show style reads return a small aggregate, for example ApplicationDetail(application, role, company, timeline, contacts, interviews).

# core/models.py  (shape, not final)

@dataclass(frozen=True, slots=True)
class Company:
    id: int
    name: str
    website: str | None
    notes: str | None
    created_at: str

@dataclass(frozen=True, slots=True)
class Application:
    id: int
    role_id: int
    status: str
    source: str | None
    resume_version: str | None
    interest: str | None
    applied_at: str | None
    notes: str | None
    created_at: str
    updated_at: str

# Role, Contact, Interview, StatusEvent follow the same pattern.

@dataclass(frozen=True, slots=True)
class ApplicationDetail:
    application: Application
    role: Role
    company: Company
    timeline: list[StatusEvent]
    contacts: list[tuple[Contact, str]]   # (contact, relationship)
    interviews: list[Interview]

The domain seam

The one architectural decision. Both the CLI now and the web app later call into the core. The question is what the core hands back and who owns the connection. Three shapes were considered.

Dimension A: Store facade + dataclasses B: function modules, explicit conn C: rows out, SQL constants
Caller writes store.add_application(company=..., role_title=...) applications.add(conn, company=..., role_title=...) conn.execute(Q.ADD_APP, {...}) then map rows by hand
Domain types Frozen dataclasses Frozen dataclasses None; sqlite3.Row or dicts
Connection and transactions Store owns them; store.tx() for multi-step atomics Every caller owns them and repeats the setup Every caller owns them
Status-event bookkeeping Inside Store, one place Inside a function, one place Nowhere to live; leaks into both frontends
Test surface Call methods on an in-memory Store Call a function with an in-memory conn Assert on SQL strings and column order
Web app later Construct a Store per request, same methods Rebuild the connection and transaction dance a second time Re-learn every column name a second time
Failure mode Class accretes methods and becomes a god object Two frontends grow two subtly different setup paths No contract at the seam; tests pin implementation

Recommendation: A, with two grafts from B. Start from the Store facade. Deletion test: remove Store and the SQL, the row mapping, the status-event transaction, and the migrate-on-open all spread into both frontends, so it earns its place. Guard the god-object failure mode by taking two things from B. First, keep each concern's SQL in its own private module (_applications.py, _contacts.py) that Store composes, so the class is a facade over small testable units. Second, expose store.tx() as a context manager for the rare caller that needs several writes to commit or roll back together.

# The caller's usage, written first. Everything else derives from this.

from job_app_track.core import Store

store = Store.open()                       # resolve path, connect, migrate to head

acme = store.add_company("Acme Corp", website="acme.example")
role = store.add_role(company="Acme Corp", title="Senior Backend Engineer",
                      arrangement="hybrid", url="https://...")
app  = store.apply(company="Acme Corp", role="Senior Backend Engineer",
                   source="referral", resume_version="v3")   # status -> 'applied' + event

store.record_status(app.id, "screen", note="30 min with recruiter")
store.set_interest(app.id, "high")
store.link_contact(app.id, contact_id=4, relationship="referrer")
store.add_interview(app.id, kind="technical", scheduled_at="2026-09-03 14:00",
                    contact_id=7)

open_apps = store.applications(status="interview")     # -> list[Application]
detail    = store.application_detail(app.id)           # -> ApplicationDetail
board     = store.pipeline()                           # -> dict[str, list[Application]]

with store.tx():                                       # one atomic unit
    store.record_status(app.id, "offer", note="verbal")
    store.set_interest(app.id, "high")

CLI surface

The CLI only parses arguments, calls one Store method, and formats the return value. Read commands take --json, which is both a scripting aid and a preview of the payload shape the future web app will serve.

jat init                              # create db, migrate to head, print the path
jat db-path                           # print the resolved db path and schema version
jat import start-data/job_app_tracker.csv   # bulk-load the old spreadsheet; refuses if apps exist, --force overrides

jat company add "Acme Corp" --website acme.example
jat company list

jat role add --company "Acme Corp" --title "Senior Backend Engineer" \
             --arrangement hybrid --url https://...
jat role list [--company "Acme Corp"]

jat apply --company "Acme Corp" --role "Senior Backend Engineer" \
          --source referral --resume v3            # creates app, status applied, one event
jat app list [--status interview] [--company "Acme Corp"] [--json]
jat app show <id> [--json]                          # app + role + company + timeline + contacts + interviews
jat app status <id> screen --note "recruiter call"

Seed data import

start-data/job_app_tracker.csv is the spreadsheet the user tracked applications in over the past two months. It is both a shape reference for the schema and the initial data set. jat import reads it with the stdlib csv module and, per row, upserts a company by exact name, inserts a role, inserts an application, and writes one status event. It creates no contacts and no interviews, because the CSV holds neither. The import refuses to run if the database already has applications, unless --force is passed.

CSV columnLands inRule
Companycompanies.nameUpsert by exact string. Variants like "Spacex", "Spacex (Starlink)", and "Starlink" become separate rows.
Positionroles.titleTrimmed. A blank cell becomes "(unspecified)" so the NOT NULL holds.
Locationroles.location, roles.arrangementRaw string to location. If it contains "remote" or "hybrid" set arrangement to match, else leave null.
Job Linkroles.urlRaw string, even when it is prose or two URLs jammed together.
Date Appliedapplications.applied_at, status event occurred_atParse M/D, M/D/YY, MM/DD. Assume year 2026 when absent. Null if the cell is blank.
Statusapplications.status + one status eventMapped, see below. Blank maps to wishlist.
Interest Levelapplications.interestHigh/Medium/Low to high/medium/low. Blank stays null.
Notesapplications.notesVerbatim.
Applied?nothingRedundant with applied_at being set. Ignored.

Status mapping, CSV value on the left:

""                          -> wishlist
"Applied"                   -> applied
"Technical Exam Screening"  -> screen
"Interview Scheduled"       -> interview
"Interview Completed"       -> interview
# "Rejected" / "Offer" / "Accepted" map straight through once they appear
Note The import is lossy on purpose. "Interview Scheduled" and "Interview Completed" both collapse to interview, and company name variants are not merged. Treat the imported rows as a starting point to clean up in the app, not a faithful copy.

Migrations

The runner reads PRAGMA user_version, applies every file whose numeric prefix is higher, each in its own transaction, and bumps user_version to the file's number. About fifteen lines.

# core/db.py  (shape)

def migrate(conn: sqlite3.Connection) -> None:
    have = conn.execute("PRAGMA user_version").fetchone()[0]
    for path in _sorted_migration_files():
        version = int(path.name.split("_", 1)[0])
        if version <= have:
            continue
        with conn:                                  # BEGIN / COMMIT, rollback on error
            conn.executescript(path.read_text("utf-8"))
            conn.execute(f"PRAGMA user_version = {version}")
Note PRAGMA user_version = ? cannot be parameterized. The value is an int() parsed from a filename that the runner controls, so the f-string is safe here and only here.

Rules for migration files: forward-only, never edit one after it has shipped, one concern per file, and every file leaves the schema runnable. Adding full-text search or a new column later is a new numbered file, not an edit to 0001_init.sql.

Deferred scope

  • The web app. The Store API and the --json payloads are designed to carry it, but no server code is in this plan. Revisit the stdlib-only rule at that point: http.server plus string.Template works, but a small framework would be a fraction of the code. That is a decision for when the CLI is proven, not now.
  • Auth and multi-user. Single user, single file, filesystem permissions. The VPN is the access control.
  • Full-text search over jd_text and notes. SQLite FTS5 is compiled into the stdlib sqlite3 on most builds; add it as a later migration when the data volume justifies it.
  • Reminders and calendar export for interviews.
  • Attachments. When resume and offer PDFs matter, store file paths, not blobs.
  • Export beyond the per-command --json read flag, and repeat CSV imports beyond the one-shot jat import.
  • Company deduplication. The importer keys on exact name, so near-duplicate company rows are expected. A merge command is later work.

Testing

Stdlib unittest. A helper builds a Store on a :memory: or tmp_path database, already migrated to head, so every test starts from an empty known schema. No mocking; in-memory SQLite is fast enough to use the real thing. The Store interface is the only seam the tests cross, which is the same seam the CLI and the web app cross.

Coverage that matters for the prototype:

  • Migrating an empty database reaches head, and running migrate again changes nothing.
  • record_status appends an event and leaves applications.status equal to the latest event, in the same transaction.
  • pipeline() groups every application under exactly one status and omits no status bucket that has rows.
  • link_contact enforces the (application, contact, relationship) primary key and rejects an unknown relationship.
  • set_interview_outcome updates outcome and debrief without touching other columns.
  • A failing statement inside store.tx() rolls the whole block back.
  • The importer maps a blank status to wishlist, parses a year-less date to 2026, substitutes a blank position, and refuses to run against a database that already has applications.

Build order

Each step is shippable and leaves the tree green. Step 1 is the approved scaffold commit.

  • Scaffold. src/ layout, pyproject.toml with the console script and package-data config, core/ modules with signatures and NotImplementedError bodies, and the complete 0001_init.sql. Lands as the first commit.
  • Migrations and db.py. Path resolution, connect() with PRAGMAs, the migration runner. Wire jat init and jat db-path. Test: migration idempotency.
  • Models and enums. The dataclasses, the canonical enum lists, row-mapping helpers.
  • Companies and roles. _companies.py, the matching Store methods, jat company and jat role commands.
  • Applications and timeline. _applications.py, apply, applications, application_detail, record_status, set_interest, pipeline, plus store.tx(). Commands: jat apply, jat app *, jat pipeline. Tests for the denorm and grouping.
  • Contacts. _contacts.py, the join table methods, jat contact *.
  • Interviews. _interviews.py, jat interview *, upcoming filter.
  • Importer. importer.py and jat import, then load start-data/job_app_tracker.csv into the dev database. Tests for the mapping rules.
  • Output polish. format.py plain-text tables and --json across all read commands.
